Key concept Architecture

Clickable Diagrams

A generated SVG carries links, so the picture stops being a dead end and becomes the navigation layer of the model.

A diagram is a picture until you can click it. Then it is an interface.

SVG is not an image format in the way PNG is. It is markup — every shape is an element, and any element can be wrapped in a link. So a generated diagram can carry, on every box, a route to the thing the box represents: the entity's documentation, its lineage, the mapping that fills it, the decision record that created it, the source table it came from.

Nothing about that is new technology. `<a xlink:href="/concepts/impact-analysis.html">` has been in the spec for two decades. What makes it powerful is what sits behind it: when the diagram is generated from metadata, the generator already knows the target of every link.

Why this changes what a diagram is for

A static picture answers one question — *how do these things relate?* — and then stops. Every follow-up question means leaving the diagram: open the catalog, search the wiki, ask someone.

A clickable diagram answers the follow-up in the place the question occurred. Click an entity and land on its definition. Click a relationship and see the mapping that implements it. Click a table in a lineage graph and jump to the transformation that writes it.

That collapses the usual gap between *seeing the architecture* and *finding out about the architecture*. They become the same act, and the diagram stops being documentation about the system and becomes a way into it.

Why it is nearly free to generate

The expensive part of a clickable diagram is knowing where each element should point. Hand-drawn, that is unbearable: hundreds of shapes, each needing a URL, all of them rotting the moment something moves.

Generated, it costs nothing extra. The generator is already walking the model to decide what to draw; the identifier it uses for a node is the identifier the target page is keyed on. The link is a by-product of the traversal you were doing anyway.

This is why hyperlinked diagrams are rare in hand-drawn practice and unremarkable in generated practice. The economics are simply different.

What to link to

| Element | Sensible target | |---|---| | Entity / table | its documentation page, or the catalog entry | | Attribute | the definition, the glossary term, the DQ rule | | Relationship | the mapping or join that implements it | | Node in a lineage graph | the transformation, the SQL, the job | | Layer or subject area | the subject-area overview | | Anything at all | the decision record that explains why it exists |

That last one is worth dwelling on. Clicking a box and landing on the ADR that created it turns a diagram into a provenance interface — the visual counterpart of *why does this exist*, answered at the point where someone is looking at the thing.

Practicalities that decide whether it works

Where it renders. SVG links work in a browser and in anything that embeds a live SVG. They are stripped or ignored in most PDF exports and in some wiki renderers. So generate SVG for the web, and keep a plain export for print — the link layer is an enhancement, not the only channel.

Relative vs absolute. Relative links survive being moved between environments; absolute ones survive being embedded elsewhere. Pick per destination, do not mix by accident.

A missing target is worse than no link. A box that looks clickable and 404s costs more trust than a box that was never a link. Validate targets at generation time and drop links whose target does not exist.
