Key concept Metadata OS

Metadata As Code

Metadata lives in version-controlled files — reviewed, tested and deployed like code, so the model is an engineering artifact rather than a GUI state.

Metadata is a code artifact, not an application's internal state. Definitions, contracts, mappings and models live in version-controlled files: reviewed in pull requests, tested in CI, deployed like anything else. No metadata trapped in a GUI, a wiki, or a vendor's repository.

The claim is deceptively small. It is really a claim about who owns the model and what can be done with it — and almost every other MDDE and BTM capability depends on the answer.

What it buys

History. `git log` on a model answers who changed a definition, when, and — with a decent commit message — why. A GUI shows you the current state and nothing else. Metadata without history cannot be audited, only trusted.

Review before effect. A change to a definition of "customer" is a diff someone approves, not a field someone edited on a Tuesday. That is the difference between governance and hope.

Branching. You can model a change without applying it — a branch, a proposal, a comparison. Modelling becomes something you can *try*, which is what makes iteration safe.

Testing. If metadata is a file, CI can check it: completeness, naming, referential integrity, contract compliance. Rules become gates instead of guidance.

Generation. Deterministic generation needs a deterministic input. Files give you that; a database behind an application does not, reliably. This is why Deterministic SQL Generation presupposes metadata as code rather than the other way around.

Why it matters more now

An AI agent can read a repository. It cannot read a modelling tool's internal state, click through a governance portal, or interpret a PNG of your model. Metadata as code is what makes a model legible to a machine — the practical precondition for anything AI-native, and one more reason models locked in tools become Gated Knowledge.

It also changes what a model *is*. Trapped in a tool, a model is a picture with a licence attached (Model as Drawing). In version control, it is an executable, testable, diffable asset that other things are generated from.

What it does not mean

Not "hand-write YAML for everything." People still model in interfaces — visual, collaborative, comfortable. The requirement is that the file is the source of truth and the interface is a view over it, not the reverse. Round-trip, not export.

Not "no database." Derived stores, catalogues and query layers are fine and useful. The rule is directional: files are authored, databases are mirrored from them. When the two disagree, the file wins.

Not free. It demands discipline that a GUI does not: naming, structure, review, merge conflicts on a model. That cost is real, and it is the same cost software engineering already decided was worth paying.
