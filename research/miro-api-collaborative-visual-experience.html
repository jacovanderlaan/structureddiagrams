# Miro API for collaborative data modelling

Question: can we connect to Miro's API so that modelling becomes a live, shared visual activity — and how does that sit against Ellie.ai and against what already exists in our own stack?

Short answer: we already built it. Twice. The interesting question is no longer can we but where this belongs in a family that now includes generated diagrams, generated palettes and an in-house board.

1. What already exists (measured, 31 Jul 2026)

Two implementations sit in C:/Repos/mdde, together 2,584 lines:

PathWhat it is
mdde-core/src/mdde/integrations/miro/The full integration: client.py · exporter.py · importer.py · layout.py · styles.py · types.py
mdde-core/src/mdde/documenter/diagrams/miro/Diagram-side: erd.py · lineage.py · miro_client.py · shapes.py

Backed by two decision records:

  • ADR-75 Miro Integration for Collaborative Data Modeling — Proposed, 11 Jan 2026. Names the problem: technical teams model in isolation with PowerDesigner or Erwin; business stakeholders cannot engage; feedback arrives late; models drift from requirements.
  • ADR-342 Miro Integration — Collaborative Data Modeling — Implemented, v3.50.0, 24 Feb 2026. Bi-directional: export MDDE models to Miro as visual ERDs, import shapes back to MDDE entities, style by classification / stereotype / layer.

The documented flow is a genuine round-trip, not a one-way export:

MDDE Metadata  ──export──►  Miro Board
(YAML/DuckDB)  ◄──import──  (Visual ERD)
      │                          │
 single source              collaborative
  of truth                  design reviews
      ▼                          ▼
 SQL generation           stakeholder feedback

Finding: the capability is built and marked implemented. What is missing is not code but placement — where this fits among the other visual modes, and whether it is still the right surface.

2. The Miro API in 2026

AspectCurrent state
VersionREST API v2; Miro pushes all developers to migrate off v1
AuthOAuth 2.0 authorization-code flow, mandatory for all apps
Scopesboards:read · boards:write (needed to create shapes) · team:read · identity:read; org-level operations need organizations:read/write
Rate limitsTiered per endpoint ("Level 2" for shape creation). Reported ceilings vary by source — roughly 100–300 requests/min per token, with 1000/min cited for some operations. Treat as: assume the low end and implement backoff.
Bulk opsCreate/update/delete up to 20 items per call; bulk connectors available
EcosystemCommunity n8n node (12 resources, 60+ operations), MCP servers, third-party wrappers — a sign the API is stable enough to build on

Practical consequence. Rate limits are the real design constraint. A 200-entity model is 200 shapes plus several hundred connectors — at 100–300 req/min with 20-item batching, a full export is minutes, not seconds. That rules out "regenerate the board on every model change" and points at export once, then sync deltas.

⚠️ Nothing found on pricing tiers for API access. Worth confirming before depending on it commercially: whether API use requires a paid plan is a business risk, not a technical one.

3. Ellie.ai — the same instinct, productised

Ellie.ai is a cloud platform for semantic data modelling. Relevant because it is the clearest commercial expression of collaborative visual modelling:

  • Real-time simultaneous modelling in the browser, with comments
  • Drag-and-drop ERD creation
  • AI chatbot that drafts an initial model for business users
  • Conceptual / logical / physical layers, business glossary
  • Role-based access, approval workflows
  • Catalog integration (Collibra, Purview), 170+ source connectors
  • Explicitly targets non-technical business users alongside data teams

Their positioning quote is worth keeping: "there are data governance/business analyst tools, and then there are data design/development tools. I don't see many connections between the two. Ellie seems to fill this gap."

Where we differ, honestly:

Ellie.aiOur approach
Source of truththe platformfiles (YAML/markdown), platform-independent
Collaborationnative, real-time, built inborrowed — Miro, draw.io, our own board
Lock-inmodel lives in their cloudmodel lives in your repo
Time to valueimmediate, it is a productbuild it yourself
Business-user accessdesigned for itthe weak spot

Ellie is better at the thing it does. The trade is ownership: their collaboration is excellent and their platform holds your model. Ours is more work and the model stays yours — which is Gated Knowledge applied to a modelling tool.

The honest conclusion: do not compete with Ellie on collaboration UX. Compete on the model being yours, in files, generating everything else — and borrow a collaboration surface when one is needed.

4. ⭐ Collaborative Visual Experience — the naming question

Jaco's phrase, and it is a good one: it names a category the field lacks a word for.

But it is broader than Miro, and that is its value. It covers every mode where people look at a model together and change it:

SurfaceWhat it isTrade-off
Miro (API)Real-time, multi-user, familiar to businessRate limits, external dependency, model leaves the repo
draw.io + generated paletteLocal, free, correct vocabulary by constructionNot real-time multi-user
Our own board (vault-mobile-site)Library rail of real linked objects → canvas → board.yamlSingle-user, ours to maintain
Ellie.aiPurpose-built productPlatform owns the model
Free whiteboardNothing constrains itNothing constrains it

The concept worth naming is not "we integrate with Miro" but: the model should be visitable — by more than one person, in a form they can change, without leaving the source of truth behind. Generated Palettes is the mechanism; Collaborative Visual Experience would be the goal it serves.

Recommendation: write it as a concept, scoped as the goal, with palettes/Miro/board as implementations. Otherwise it reads as a feature list rather than an idea.

5. Integrating into our own apps

Jaco's question: "can we integrate this functionality into our apps?" Three routes, in increasing cost:

A · Extend the existing board (cheapest). vault-mobile-site already has the pattern: library rail, free-drag canvas, board.yaml. Missing is multi-user. Adding real-time is a large step; adding asynchronous collaboration — share a board, comment, diff two versions — is not.

B · Miro as the collaboration surface, files as truth. Use the built integration for the moments that need a room: workshops, design reviews, stakeholder walkthroughs. Export → collaborate → import → the model absorbs the outcome. Miro is the meeting room, not the filing cabinet.

C · Build a real-time collaborative canvas (most expensive). This is competing with Ellie on their strongest ground, and it is a product in itself. Hard to justify unless collaborative modelling becomes the offering rather than a feature of it.

Recommendation: B now, A incrementally. The Miro integration already exists; the marginal cost is documenting and demonstrating it, not building it. Route C is a different company.

6. Conclusions

1. Built, not hypothetical. 2,584 lines across two modules, ADR-342 marked Implemented. The next step is not development but a working demo and an honest write-up.

2. Rate limits shape the design. Export-once-then-delta, not regenerate-on-change. Assume 100 req/min and back off.

3. Miro is a meeting room, not a source of truth. Round-trip only; the model returns to files.

4. Do not out-collaborate Ellie. Compete on ownership and generation, not on real-time UX.

5. Name the category. Collaborative Visual Experience as the goal; palettes, Miro and the board as implementations.
